#72 实盘前双账户隔离实施计划

**目标**：在不连接实盘账户、不启动第二套 scheduler 的前提下，用双账户夹具证明 paper/live 的订单、成交、持仓、信号和只读页面不会串账，并消除两套 scheduler 使用相同确定性订单号时的数据库冲突。

**不在本批范围**：切换 `TRADING_MODE=live`、配置实盘密钥、发送实盘订单、启动第二套 scheduler、用真实实盘数据验收、组合页 paper/live 对比视图。上述内容继续受 #35 的书面授权门禁约束。

## Task 1：订单与成交的模式隔离

1. 先补失败测试：同一个 `client_order_id` 可分别属于 paper/live，但同一 mode 内仍唯一。
2. 新增 Alembic 迁移，把 `orders.client_order_id` 的全局唯一约束改为 `(mode, client_order_id)` 复合唯一约束；历史数据无需改写。
3. Executor 的重试序号、恢复、状态更新、broker order 查询和 fill 幂等查询全部同时限定 `mode`。
4. 回归测试覆盖：另一 mode 的相同 client/broker order id 不影响当前 mode 的重试、恢复、更新与成交写入。

## Task 2：双账户 API 隔离矩阵

1. 扩展测试夹具，使 paper/live 能同时写入相同自然订单号、不同账户数值。
2. 在同一数据库中同时构造两个账户，逐项验证：meta 默认账户、组合概览/持仓/绩效/订单/成交/信号、个股关系与成交、系统任务/风险、盘中持仓估算。
3. 行情、回测等账户无关数据保持共享；测试明确区分“共享市场数据”和“按 mode 隔离的账户数据”。

## Task 3：前端账户传播

1. 补 SystemPage、StockPage 的 live 请求测试，断言查询参数始终使用当前查看账户。
2. 保留现有顶栏实盘橙色标识、浏览器标题、默认实盘和禁用无数据账户测试。
3. 静态护栏确认面板没有修改服务器交易模式或交易开关的入口；账户切换只修改 URL 查询参数。

## Task 4：验证与交付

1. 运行定向后端、前端测试及迁移升级/降级测试。
2. 运行 `make check`。
3. 合入 `test` 并等待 CI；本批不自动授权 Phase 5，也不关闭 #72，真实数据和双 scheduler 验收继续保留。
