## 请求预算与隔离

- quotes 中报价与资讯使用同一个 Finnhub 客户端串行执行，资讯在报价轮次之间运行。
- quotes、夜间 market_extras、stock_data 的客户端都通过共享数据卷上的文件锁协调，两次请求至少间隔 1.1 秒（请求结束后计时，保守限制）。没有把密钥写入锁文件。
- 约 525 次报价 + 至多约 40–50 次新闻/财报请求（取决于持仓数），受网络时延影响，页面给出的周期是预期值，不是时效保证。
- quotes 不加载老虎配置，也不导入 broker / executor；采集失败不触发交易操作。交易 scheduler 不增加盘中工作。仍共享 PostgreSQL、磁盘、CPU，不能称为物理隔离。
- quotes 保持 0.5 CPU / 512 MiB 容器上限。来源限流、网络阻塞和数据陈旧由日志、采样及界面时间反映。

## 本地离线基准（实测）

命令：`uv run python scripts/research/refresh_benchmark.py --rounds 5`。

- macOS 14.1.1、x86_64，本地未施加服务器容器的 CPU 限额。
- 合成 503 只成分股 + 22 只 ETF，260 个交易日，覆盖率 100%。
- 五轮耗时：4.3106 / 4.5206 / 4.4838 / 4.8391 / 4.8114 秒。
- 五轮进程 CPU 时间：4.5470 / 4.7481 / 4.7195 / 5.0527 / 5.0020 秒。
- 进程峰值 RSS：174,399,488 字节（约 166 MiB，包括运行时与样本构造，非容器实测）。
- 单个首页快照：493,528 字节（约 482 KiB）。

只测计算和本机文件读写，不含真实 HTTP、PostgreSQL upsert/WAL、服务器容器争用，不代表线上同样耗时。#93 原有实测为 525 只、一轮 11.4 分钟、覆盖率 99.8%，是旧版本的一次采集记录，不能当作新版本整日压测。

## 数据盘估算与边界

以 11.4 分钟/轮、常规时段 390 分钟粗算约 34–35 轮，每天约 1.8 万次报价 upsert。实际资讯刷新会占用同一采集循环，轮数可能减少。

- 行情表约几百行，每股覆盖更新，不保存逐分钟历史。持仓/关注列表变动可能留下少量旧代码行。
- 按上述快照大小，35 次覆盖的逻辑写入约 16.5 MiB/交易日；最新文件仍只有约 482 KiB。**这不包括 PostgreSQL WAL、旧行版本、索引、日志、文件系统写放大和日线补数。**
- 有界资源日志最多 128 条，每条记录耗时、CPU 时间、进程峰值内存、请求数、429 数、报价写入数、快照大小、覆盖率和时间范围，覆盖更新文件。
- 不能由逻辑写入估算整个数据盘的每日增长；数据库 vacuum、备份、Docker 日志和其他任务都要同时观察。

## 线上完整交易日验收（待执行）

monitor 自动每 5 分钟（在下一采样轮次执行，可能稍晚）保存一条 `system_metrics(kind='capacity', name='refresh')`，沿用 8 天保留：数据库与 WAL 累计值/重置时间、报价表行数/大小/dead tuples、最新报价、日线/盘中快照和资讯文件日期，以及最近 quotes/extras 轮次摘要。SQL 限时 3 秒，数据库或文件不可读会记录 unavailable，其他资源采样继续保存。只存白名单字段，不保存新闻正文或配置。

原有容器采样同时记录 Docker 提供的块 I/O 累计读写字节；没有计数时留空，不能当作零。对齐 `started_at`/重启数再算差值。WAL 是整个 PostgreSQL 集群的量，不能直接全归因于报价；CPU/内存为采样最大值，可能漏掉短暂峰值。至少覆盖一个完整交易日及前后基线后再验收，部署前空缺不能补造。

只读查询：`SELECT ts, extra FROM system_metrics WHERE kind='capacity' AND name='refresh' ORDER BY ts DESC LIMIT 3;`。与同时间 host/container 采样及 job_attempts 对照；需要在 8 天内导出仓库外分析，不能依靠有界 refresh_metrics.json 还原长期历史。

手动补充采样仍可使用：

在服务器部署目录运行 `python3 /path/to/scripts/refresh_capacity_sample.py`。脚本只调用只读 Docker stats/df、数据库 SELECT 和读取资源缓存；不访问券商、不重跑交易任务。

交易前、盘中每 5 分钟、收盘后采样到仓库外 JSONL。结合现有 monitor 观察：

1. quotes 的 CPU/内存峰值、OOM/重启；主机资源与 scheduler 任务是否按时完成。
2. 每轮耗时、报价覆盖、最老报价年龄、429 次数；新闻/日历缓存是否推进。
3. 数据库大小、报价表大小与 dead tuples；WAL 累计增量（同一 stats_reset 下），磁盘实际增长；日志大小另测。
4. 交易开盘、调仓及收盘期间没有人工干预交易任务；对照 #34 的任务记录。

验收门槛：无 OOM/新增重启；盘中正常轮次报价覆盖率至少 90%；完整轮次最老报价不超过 20 分钟，超时有明确状态；无持续 429；新闻/日历按预期推进；无因资源争用造成的交易任务失败；磁盘有充足余量。保留异常区间与来源故障说明，不通过调大阈值隐藏失败。
